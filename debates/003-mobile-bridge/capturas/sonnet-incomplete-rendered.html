Brief — up to 300 words

Recommendation. Build one small public HTTPS MCP server, the relay, with an append-only ledger. Attach it as a custom connector to both phone apps: ChatGPT for intake and status, Claude for the King. Add an outbound-only courier on the PC. The courier claims work from the relay and starts the existing Right Hand with codex exec. The relay is the control plane for requests, state, packet parts, decrees and execution records. The Council repository stays the artifact plane and is written only from the PC checkout.

Why.

  • Both phone apps are documented MCP clients, and connectors added on the web sync to mobile.
  • Neither app can reach the PC or the repository directly.
  • A public relay is the one boundary both apps can call, and outbound polling is the one way to start local work without opening the PC to inbound traffic.
  • Authority comes from connector scopes, not message text. The King’s connector can write plans and decrees. Sovereign overrides need a human tap on a relay page.

Main alternative. GitHub as the transport, using issues or dispatch events, a self-hosted runner and @codex. @codex starts Codex cloud tasks, which breaks R2. GitHub also gives ChatGPT no write path, so a relay is still needed.

Failure conditions.

  1. Martim’s ChatGPT plan cannot call write tools on custom connectors. The documentation is contested. The fallback is a link-tap intake.
  2. codex exec cannot drive the browser tools the coordinator uses today. This is unknown. If so, the PC trigger is unresolved.
  3. Claude mobile cannot ingest the chunked packet whole. The fallback is manual attachment.

Check. Run three probes (Stage 0) before building anything else.

2.2 Ledger record, common contract

Every record has:

  • a server-assigned record_id
  • debate_id
  • revision (the git commit SHA the record refers to, or null before a debate exists)
  • kind
  • author_role (sovereign, king or device)
  • auth_basis (connector scope plus confirmation basis)
  • payload_sha256
  • state
  • supersedes
  • timestamps

Records are append-only. State changes are new records. Free text in a payload is data and never grants authority.

2.3 The four connections

A. Phone → PC (request, then launch)

  1. Martim tells GPT-6 Normal what Council he wants.
  2. Normal calls draft_request(text). The relay stores a draft and returns the stored text and its digest.
  3. Normal calls confirm_request(draft_id, digest). This is a write and relies on ChatGPT’s own tool-approval dialog. It creates a request record in state submitted. This is the sovereign act that starts a context draft.
  4. The courier long-polls claim_next and receives the request. It checks that the workspace path exists, that origin equals the stated remote, and that the working tree is in a known state. It then starts or resumes the Right Hand with the request as input.
  5. The Right Hand drafts CONTEXTO.md and commits it. The courier reports context_ready with that commit SHA.
  6. Martim sees this through status, then authorizes launch with confirm_launch(debate_id, context_commit). The authorization is bound to one context revision, which mirrors “authorized for launch” in the existing practice.
  7. The Right Hand runs the phases as in debate 002 under v2.1. The courier reports each phase transition (for example proposals_collecting, proposals_closed@<sha>, reviews_closed@<sha>). Any decision reserved to Martim, such as an absent participant, becomes awaiting_sovereign with explicit options.

B. State → phone

  • get_status(debate_id?) returns, per debate:
    • the state and the next action for the sovereign
    • the revision (commit SHA) the state refers to
    • the ledger as_of marker
    • the last courier heartbeat and a flag pc_current: confirmed | unconfirmed
    • the source of each field (ledger event, or the relay’s own read of the GitHub remote)
  • When the heartbeat is stale or the relay cannot verify the remote, the answer says “last known, current state unconfirmed”.
  • Status contains metadata only. It never contains the bodies of staged or closed contributions. This keeps Normal, which is also an adviser, from being exposed to other participants’ material through the status path (R7).

C. Synthesis → Claude phone app

  1. After reviews close, the Right Hand assembles the King packet from the closed commit: Laws, rules, context, operating model, manifest, all closed proposals and reviews. The courier uploads it.
  2. The relay stores it in numbered parts, each with its own SHA-256, plus an overall digest, a section inventory and an end marker such as END-OF-KING-PACKET-<debate>-v<n>. The digest is recorded in the ledger, not inside the packet.
  3. Status tells Martim the packet is ready and what to say in the Claude app. This is the one trigger that cannot be automated, because I found no documented way to push content into a Claude phone conversation.
  4. Martim opens a conversation with Opus and sends one short instruction. Opus calls king_get_packet(debate_id, version, part) for each part.
  5. Opus calls king_ack_receipt(debate_id, version, parts_received, end_marker). The relay compares this to the stored manifest. Any mismatch or missing part returns the missing list and the record stays receipt_incomplete. The King then re-fetches. A synthesis claiming completeness without a matched receipt is flagged in the ledger.
  6. Opus submits the plan with king_submit_plan(...), which carries the receipt’s record_id. It then submits the decree with king_submit_decree(plan_record_id, text).

D. Decree → Codex

  1. The relay validates the decree: King scope, a plan record that exists, a matching receipt, and a digest.
  2. The courier claims it. The Right Hand commits PLANO-FINAL.md and DECISAO.md verbatim into the checkout. The commit message carries the record_id and payload_sha256. The commit SHA is reported back, and that SHA is the “plan revision” for everything after.
  3. Sovereign gate. The decree stays recorded until released or amended. Martim may release it, veto it, or amend it, through confirm_release, confirm_veto or confirm_amend(decree_id, text). These records are created only through the relay confirmation page, as a human tap by Martim on an authenticated session. The Claude connector has no scope for them, so Opus cannot create a sovereign record.
  4. After release, the courier resumes the Right Hand with the decree, or the amended decree, and the exact commit. The Right Hand implements the decree, records an execution file in the repository and reports an execution record containing the commit range.
  5. The relay makes a review packet from the decree and the execution record, with the same part and digest scheme. The King fetches it in the Claude app and submits king_submit_review(execution_record_id, verdict, objections).
2.4 State machines and idempotency (R6)
  • Request: draft → submitted → claimed → context_ready → launch_confirmed → running → …. A request for which launch is never confirmed stays context_ready and is never launched implicitly.
  • Decree: submitted → validated → claimed → recorded_in_repo → released | vetoed | amended → executing → executed → under_review → reviewed.
  • Idempotency keys:
    • A request is identified by the digest of its normalized text. Re-submitting identical text while a request is open returns the same record_id and its current state. It never creates a second debate.
    • A decree is identified by (debate_id, plan_record_id, payload_sha256). Re-submitting returns the existing record.
    • A different decree text against the same plan revision becomes conflict and needs a King resubmission or a sovereign decision.
    • An amendment is a new record that points at the decree it amends. It never rewrites the decree.
  • Claims are leases that the courier must renew through the heartbeat. A lapsed lease marks the work claimed_unconfirmed. On restart the courier reconciles the local execution journal and git state against the ledger before re-running anything. The work is then continued, marked complete, or marked failed, never re-executed blindly.
  • Execution journal: for each claimed item the courier writes record_id, commit-before and commit-after to a local journal file outside the repository, so an interrupted run can be resolved from facts.
2.5 Authority and untrusted text (R5, R8)
  • Role comes from the scope of the credential that made the call.
  • Proposal text, review text and tool output are data. The relay never converts text into an authority marker.
  • The device credential cannot author a request, decree or amendment. The ChatGPT connector cannot write plans or decrees. The Claude connector cannot create sovereign records.
  • Packet bodies contain arbitrary participant text. That text could attempt to induce a tool call, such as a fake instruction to submit a decree. Defences:
    • king_submit_decree is rejected without a matched receipt for the same packet version.
    • Per-call approval in the apps is assumed, not verified.
    • Status shows Martim the recorded decree text before it is released, so he can veto it.
  • Pending premise: whether execution waits for an explicit sovereign release or starts on decree receipt. I recommend the gate, because a veto after execution cannot be undone by the ledger. The relay supports both. Martim chooses, since this touches the Laws’ veto and amendment authority.

3. Alternatives

  1. GitHub-native transport. Requests become issues or comments, a self-hosted runner reacts to dispatch events and runs codex exec, and @codex handles cloud work.
    • It would put one record in git, which is attractive.
    • @codex mentions create Codex cloud tasks, which do not run in the PC checkout or drive the PC’s browser tools. That breaks R2. A self-hosted runner could run locally, but ChatGPT still has no documented write path into GitHub, so a write-capable connector is needed anyway.
    • Phone connectors for GitHub differ by app, and I could not confirm one for the Claude phone app.
    • Duplicate cloud tasks from a single mention were reported in a public Codex issue, which is a risk for R6.
    • A viable variant is to use GitHub as the ledger behind the same MCP relay. I prefer a relay-owned ledger because status needs heartbeats and claim states that would otherwise be committed as noise into the Council record.
  2. Manual relay by Martim. Copy and paste each message between apps. It meets none of the automation and is only the fallback.
  3. Remote desktop from the phone into the Codex app. It reaches the active Codex task, but it breaks the ChatGPT and Claude entry points, gives no authority attribution and gives no status. It is not recommended.

By criterion, in priority order:

  1. Authority and complete delivery. Strongest in this design: each boundary has a named receiving operation, authority is carried by scopes, and the receipt check is explicit.
  2. Demonstrated capability. The plan labels what exists (documented MCP clients, codex exec) against what must be built (relay, courier) and what is unverified.
  3. Correct state and recovery. Covered by queued, unconfirmed, receipt_incomplete, conflict and the reconcile step.
  4. Fit to the phone surfaces. Entry and status are in ChatGPT, the King is in the Claude app, and every required manual action is stated.

Refutation tests

  1. Write probe. If a write tool call from the ChatGPT phone app is refused or not offered on Martim’s account, I abandon direct intake in favour of the link-tap fallback.
  2. Headless browser probe. If a codex exec session started by the courier cannot perform a browser action in a fresh page, the PC trigger as designed is not established, and I withdraw the recommendation until another start mechanism is shown.
  3. Packet ingestion probe. If the Claude phone app does not return all parts with matching digests, I change to manual attachment for the King handoff.
  4. Duplication probe. Submit the same request twice and the same decree twice. Anything other than one debate and one execution refutes the idempotency design.
  5. Authority probe. Ask Opus, in the Claude app, to create a veto record. If the relay accepts it, the scope separation fails and the design is wrong.
