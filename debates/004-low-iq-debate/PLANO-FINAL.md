## Recommendation

**Adopt a measurement-first, evidence-gated plan on one frozen workload, built on the optional paths the code already has, with exact-class edits only where the measured profile shows a share to win.** Nothing is changed in the live campaign by this plan.

The decisive reasons:

1. **No bottleneck is established.** U1, U2 and U3 are open. The only current facts are the code and the hardware inventory (`SNAPSHOT-NOTES.md`, «Existing evidence and its limits»). The dated reports measured an older pipeline (`train.py`, 2,048 samples per game, a checkpoint named `deployed_5020games.pt`; `PERFORMANCE.md`) or other campaigns. A plan that ranks targets before a profile exists would be ranking unmeasured phases (R2).
2. **The loop has a measurement gap that decides U2.** `execution['learner_seconds']` wraps only `trainer.update()`. `trainer.ingest()`, `trainer.investigate()` (real rollouts against the external engine, on the learner process), `record()`, `metrics()` and `save()` run on the same thread outside it (`train_cognitive.py`, main loop). Only deepseek raised this. It is decisive, and the plan adopts it (D2).
3. **Exact state equivalence is unattainable by construction at more than one actor.** `CognitivePool.receive()` uses `wait(..., FIRST_COMPLETED)`, so the order in which games reach the learner depends on timing. Any change, including the status quo, then produces a different trajectory run to run. Only deepseek raised this as the basis of the gates. The plan adopts it (D3): exact gates are valid only at one actor with a fixed replay corpus and seeds. At the campaign's worker count, a change is accepted against the baseline's own run-to-run band.
4. **The strongest hardware idea is real, and the code says so.** `--learner-device cuda` needs no missing module. `tonkai.cuda_learner` is imported only under `--cuda-graphs` (`train_cognitive.py:229-231`), and the learner device comes from `cfg.resolved_device()` (`survival_trainer.py:97-98`, `config.py:81-86`). Glm's proposal tied the GPU learner to reviewing the absent file, and deepseek's Stage 3a sentence reads the same way (its risk table limits the gap to the graphs path). That reading is refuted by the code. The plan therefore carries the CUDA learner as a first-class trial branch (D8), not as an unverified one. `--cuda-graphs` stays blocked until `cuda_learner.py` is supplied.
5. **Several proposed mechanisms fail on the code.** The snapshot cache keyed on a step counter cannot hit in steady state and would go stale (D7). Vectorizing `_piece_loss` on the device changes the draw order of a checkpointed RNG (D8). A bit-identical gate on tolerance-bounded paths would reject beneficial flags (D3). In-flight depth beyond the worker count changes policy lag (D6).

What is deliberately **not** decided here, because the basis does not exist yet:

- **Which acceptance workload** (U1). Martim designates it, or an observed launch record identifies it (D1).
- **Which optional paths and sizes win.** Stage 0 and Stage 1 decide, with gates fixed now.
- **The numeric tolerance for changes that alter arithmetic** (U4). The plan fixes how the bound is obtained (D3). Martim may tighten it or veto any change.

## Architecture and operation

The loop under study is serial at the centre and parallel at the edge:

1. **Learner process** (`train_cognitive.py::main`). One thread, `torch.set_num_threads(1)`. Per received game: `ingest`, `investigate` every `experiments_every` games, then `updates_per_game` calls of `update()` (8 sequences × 48 learned states, burn-in 16, future horizon 8 in the defaults), then bookkeeping, checkpoint and metrics. The optional broker thread lives here.
2. **Actors** (`CognitivePool`). `num_workers` spawn processes, each owning an external engine and, with a mixture, a Fairy-Stockfish engine. They receive a pickled snapshot per game, play it, and return an episode and trace.
3. **Coupling.** `submit` happens only after the learner has finished the previous game's work, and `receive` returns the first finished game. The snapshot an actor plays with is therefore older than the learner's weights by the games in flight. That lag is part of the learning semantics, which is why worker count and in-flight depth are Class B (D3, D6).

How the plan's parts fit together:

- **D1 + D2** produce the frozen workload and the profile. They change no behaviour.
- **D3** is the gate vocabulary every later step uses. **D10** is the acceptance protocol and the state-safety rules around it.
- **D4, D5, D6, D7, D8** are candidate families. Each is *opened or closed by the Stage 0 profile* and *confirmed or dropped by its own paired result*. They compose only after each has survived alone.
- **D9** is the fence: what the plan will not do without Martim.

The sidecar writes additive JSON into the same `execution` dictionary the loop already emits, so existing readers keep working. All candidate code lives behind flags, so rollback is a relaunch without the flag from an untouched checkpoint.
